# Rolls Bar — что ещё нужно получить от клиента

Updated: 2026-10-09

Цель этого списка — запросить данные у клиента **одним сообщением**, а не возвращаться к нему по одному пункту. Ничего из этого нельзя угадывать или подставлять самостоятельно.

## Обязательно для первого запуска

### 1. Рабочая почта для новых заказов
Нужно получить:
- точный e-mail, на который оператор должен получать новые заказы;
- по возможности название почтового сервиса/провайдера, где этот ящик уже работает (например: Яндекс 360, Mail.ru/VK WorkSpace, Gmail/Google Workspace, REG.RU или другой).

После получения:
- настроить WooCommerce recipient;
- подключить надёжный почтовый транспорт/SMTP, если он требуется конкретному провайдеру;
- секреты хранить только в защищённом server/GitHub secret store;
- сделать один настоящий тестовый заказ на staging;
- подтвердить, что письмо реально пришло оператору и содержит нужные данные один раз.

Пароль от почты нельзя хранить в Git или обычном чате. Если для SMTP потребуется пароль приложения/ключ, способ безопасной передачи согласуется отдельно.

### 2. Telegram для заказов
Текущее решение владельца проекта: Telegram обязателен для первого запуска, и в операторском сообщении разрешены имя, телефон и адрес клиента.

Нужно получить/организовать:
- Telegram-бота для уведомлений;
- chat ID личного чата или группы, куда должны приходить заказы;
- bot token — только через защищённое хранилище, не в Git/обычной переписке.

После подключения сделать реальный staging-test и проверить:
- сообщение пришло;
- номер заказа;
- сумма;
- способ получения;
- состав заказа;
- имя;
- телефон;
- адрес и дополнительные адресные поля;
- комментарий клиента;
- отсутствие дублей;
- заказ создаётся даже при временной ошибке Telegram.

## Нужны позже, но не блокируют текущую разработку

### 3. Точные границы зон доставки
Если клиент хочет автоматическое определение зоны/минимальной суммы по адресу, нужны точные границы каждой зоны.

Уже известные пороги минимального заказа хранятся в системе, но реальные полигоны нельзя строить приблизительно.

После получения:
- внести реальные полигоны;
- проверить точки внутри/снаружи/на границе;
- только после QA включить courier enforcement.

До этого автоматическое применение полигонов остаётся OFF.

### 4. Финальная анкета вакансий
Если клиент хочет полноценную форму отклика, нужны:
- финальные вопросы анкеты;
- куда должны приходить ответы;
- при необходимости текст согласия/дополнительные условия.

Пока этого нет, публичная страница вакансий остаётся production-safe без технической заглушки и без выдуманной анкеты.

## Только если клиент отдельно заказывает

### Яндекс Метрика
Текущее решение владельца проекта: не входит в обязательный первый запуск, можно продавать отдельной работой.

Код интеграции уже подготовлен. Если клиент заказывает Метрику, понадобится ID его счётчика; затем подключаются и проверяются цели.

### Онлайн-эквайринг
Текущий первый запуск — **оплата при получении**.

Для отдельного этапа онлайн-оплаты потребуются:
- окончательно выбранный банк/провайдер;
- договор/merchant-настройки;
- sandbox/production credentials через защищённое хранилище;
- callback/refund QA.

Не выбирать провайдера только по старым упоминаниям банка в переписке.

## Готовое сообщение клиенту

Можно отправить клиенту этот текст без технических деталей:

> Николай, чтобы мы закрыли оставшиеся интеграции сайта, пришлите, пожалуйста:
>
> 1. Рабочую почту, на которую должны приходить новые заказы. Если знаете — напишите ещё, где эта почта работает (Яндекс, Mail.ru, Gmail, REG.RU или другой сервис). Сам пароль пока не присылайте.
> 2. По Telegram: куда должны приходить уведомления о заказах — в личный чат или группу. Если бот уже есть, напишите об этом; если нет, подскажем коротко, как создать и добавить его.
> 3. Если уже готовы точные границы зон доставки — пришлите их в любом удобном виде. Если ещё уточняете, это можно доделать позже.
> 4. Если нужна форма отклика на вакансии — пришлите финальные вопросы анкеты и куда должны приходить ответы.
>
> Метрика и онлайн-оплата сейчас не нужны для запуска: их при необходимости можно подключить отдельным этапом.

## Что НЕ нужно запрашивать повторно

Не просить клиента повторно данные, которые уже находятся в подтверждённом проектном источнике. Перед новым запросом всегда сверять live Project No Loss/ТЗ.

## Возврат после ответа клиента

Когда клиент пришлёт данные:
1. перечитать live GitHub/Project No Loss;
2. не повторять уже пройденные acceptance/recovery/admin/operator тесты;
3. подключить только новые внешние интеграции;
4. провести targeted end-to-end email/Telegram QA;
5. если пришли полигоны/анкета — закрыть соответствующий deferred-блок отдельно;
6. заморозить точный release SHA только после текущих launch-интеграций;
7. финальный GO/NO-GO;
8. production — только после явного разрешения владельца.
